# Streaming Server Agent

A per-server HTTP agent that runs your deploy/update/delete/alias/cleanup
operations, so your control panel can trigger them over an authenticated API
instead of SSH. Returns a **job ID** immediately and streams **live logs** over
SSE.

> **Security posture.** The agent runs as **root** (it invokes root-level deploy
> scripts). Its bearer token is therefore equivalent to root. Protect it: bind to
> a private/VPN interface, set an IP allowlist, and keep the token secret.

## Status: fully native

The server, auth, job runner, and SSE are complete, and **all five operations
are native JS** — the agent reimplements the deploy/update/delete/alias/cleanup
logic itself and no longer shells out to the `.sh` scripts. The scripts remain
only for manual SSH work; the agent is the source of truth for API-driven ops.

Operation logic lives in `src/operations/*.js`, built on shared helpers in
`src/lib/*` (system/process/git in `sys.js`, `.env` read/write in `envfile.js`,
nginx/cron/wo scaffolding in `site.js`, the SEO/CDN HTTP calls in `api.js`, the
domain-map resolver in `map.js`, and the global constants in `siteConfig.js`).

Because the API has no TTY, the interactive gates from the scripts become
parameters: `delete` requires `confirm:true`, `deploy` requires `root` (no DB
selector — creds resolve from the map), and `cleanup` uses `mode:replace`
(the interactive `all` mode is rejected).

### SSL: Let's Encrypt or a custom certificate

`POST /api/op/ssl` with `{ domain }` re-issues Let's Encrypt. With
`{ domain, cert, key }` (PEM) it installs a pasted certificate instead:

- the pair is validated **before** the job is queued — key matches the cert, the
  cert covers the domain (SAN/wildcard), not expired, key not passphrase-protected
  — so a bad paste is a `400` with the reason;
- files go to `/etc/ssl/wcp/<domain>/` (key `0600`), outside `/etc/letsencrypt`
  so acme.sh never touches them; the site's `conf/nginx/ssl.conf` keeps its own
  `listen` lines and only the certificate lines change; an HTTP→HTTPS block is
  added if the site had none;
- `nginx -t` gates the reload, and everything is restored if it fails;
- the key is redacted from job views and dropped from memory after the run.

A custom certificate does **not** auto-renew. Re-issuing Let's Encrypt switches
back. `GET /api/sites` reports each site's `ssl` (`letsencrypt` | `custom` |
`none`) and `ssl_expires`, read from what nginx is actually configured with.

### WWW preference

Per site, one of `nonwww` (default: `www.<domain>` is served and 301s to
`<domain>`), `www` (the reverse) or `off` (`www` is not served, and Let's Encrypt
is issued with `--letsencrypt=subdomain` so a missing `www` DNS record can't fail
it). Set at deploy time (`www` param of `deploy`/`alias`; absent = keep the
site's, else WordOps' own choice) or on a live site with
`POST /api/op/www { domain, mode }`.

The redirect is an nginx server block (not WordPress), `WP_HOME` is kept in step
so the two never fight, and caches are purged when the host changes. Switching to
`www` is refused — before anything changes — if the certificate doesn't cover
`www.<domain>` (a Let's Encrypt cert is re-issued with it first). The mode is read
back from the vhost, so `GET /api/sites` reports `www` for every site; a vhost
written before this feature reads as `nonwww`, which is what it did.

### Backup sites + cron on/off

A **backup** is the same site deployed again on another server (`deploy`/`alias`
with `backup: true`): same shared DB, same code, `.env` gets `SITE_BACKUP=1`, and
its cron file is written as `/etc/cron.d/<name>.disabled` — cron ignores names
with a dot, so the jobs exist but never run. SSL and brand/CDN registration are
skipped (DNS points at the primary). `POST /api/op/cron { domain, active }`
renames the file on/off and restarts cron; the portal's monitor does this by
itself, but only for a disaster (primary server AND site down). `POST
/api/op/root { domain, root }` records `SITE_ROOT_DOMAIN` on an older site. `GET /api/sites` reports `backup` and `cron`
(`on`|`off`) per site.

### WordPress users

`POST /api/wp/users { domain }` lists a site's users and the roles it defines.
`POST /api/wp/users/:action { domain, … }` changes one:

| action | input | notes |
|---|---|---|
| `create` | `login, email, role` | no e-mail is sent; returns `password` once |
| `reset` | `id` | new password, all sessions ended; returns `password` once |
| `set-role` | `id, role` | refused for the last administrator |
| `deactivate` | `id` | roles removed (remembered in user meta), password scrambled, sessions ended |
| `activate` | `id` | roles restored; returns a new `password` once |
| `delete` | `id, reassign` | posts go to `reassign`; refused for the last administrator |

Everything runs in one wp-cli process (`scripts/wp-users.php`) with the input as
JSON on **stdin**, so a password is never in argv. Passwords are generated by
the agent (32 random characters). These calls are answered directly rather than
queued as jobs, so a password never reaches a job log.

### Database backups (DigitalOcean Spaces)

| Call | What it does |
|---|---|
| `POST /api/op/dbbackup` | Every database the map names (or those of `roots`): `mysqldump` → gzip → Spaces, then retention (`keepLast`, `maxAgeDays`; the newest backup is never deleted). A failing database does not stop the others; the job fails at the end if any did. |
| `POST /api/op/dbrestore` | `{ key, root, confirm }`: download the backup, take a safety backup of the target (`…_pre-restore.sql.gz`), then import. `confirm` must be the target database's name. |
| `POST /api/backup/list` | What is in the bucket, plus which root domains use each database. |
| `POST /api/backup/test` | Lists, writes and deletes a probe object. |

All take `s3Endpoint, s3Region, s3Bucket, s3Key, s3Secret, prefix` (flat names, so the
job view redacts the key and secret). Objects are stored as
`<prefix>/<db-server>/<database>/<kind>/<database>_<UTC stamp>.sql.gz`, where
`kind` is `scheduled` (retention prunes these) or `manual` ("Back up now" and
pre-restore safety copies — never deleted by the agent). S3 requests are
signed with Signature V4 in `src/lib/s3.js` — no SDK; one object is capped at
5 GB (single PUT). Dumps pass through `BACKUP_DIR` (default
`/var/backups/db-backups`) and are removed after upload. Timeouts:
`AGENT_BACKUP_TIMEOUT_MS` (6 h), `AGENT_RESTORE_TIMEOUT_MS` (3 h).

### Malware scan (ClamAV)

`POST /api/op/scan { domain }` scans `/var/www/<domain>/htdocs` with `clamscan`
(skipping `.git` and the page cache). ClamAV is installed by the first scan and
the signatures are refreshed when older than a day. Every hit is logged, and
the job FAILS when anything is found so it stands out. The full report is
written to `SCAN_REPORT_DIR` (default `/var/backups/clamav`) and served by
`GET /api/scan/report/:jobId`; the portal offers it as a download from the
operation's log. Timeout: `AGENT_SCAN_TIMEOUT_MS` (2 h).

### PHP package updates

`POST /api/op/phpupgrade` runs `apt-get update` and `apt-get install
--only-upgrade` for every installed `php*` package (non-interactive, existing
config files kept), restarts each `php*-fpm` and re-applies the tuning. It moves
a version to its newest patch release (8.3.26 → 8.3.36); it never changes a
site's major version. `/healthz` reports `php` (`php -v`) so the portal can show
who is patched.

### PC / MOB pairing

An alias (`SITE_ROLE=clone`) names its main in its own `.env`: `SITE_MAIN_DOMAIN`
(written by the alias deploy) or, for older aliases, the `SITE_CANONICAL_HOST` it
inherited. `GET /api/sites` pairs sites from that, so a main can have several
aliases (`aliases: [...]`) and stays paired after it is redeployed. The main's
`SITE_MOBILE_HOST` holds one alias only and is a fallback; a main redeploy now
restores it from the aliases present.

## Install

**Full fresh-VPS walkthrough — including WordOps, Redis, Node, and Tailscale — is
in [`INSTALL.md`](INSTALL.md).** The short version, once the host already
has WordOps + Node 18+ installed:

```bash
sudo mkdir -p /opt/streaming-agent
sudo cp -r src package.json streaming-agent.service /opt/streaming-agent/
cd /opt/streaming-agent
sudo npm install --omit=dev
sudo cp .env.example .env
# edit .env — at minimum set AGENT_TOKEN (openssl rand -hex 32)
sudo nano .env
```

Run under systemd (the unit targets `/opt/streaming-agent`):

```bash
sudo cp /opt/streaming-agent/streaming-agent.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now streaming-agent
sudo journalctl -u streaming-agent -f
```

## Prerequisites

The host must have **WordOps** (which brings nginx, PHP, MariaDB with
`mysqldump`, wp-cli, certbot), **Redis** (`wo stack install --redis`),
**Node.js 18+**, plus `git` and `sed`. See [`INSTALL.md`](INSTALL.md).

## Configuration

See [`.env.example`](.env.example). Key vars: `AGENT_TOKEN` (required),
`AGENT_HOST` / `AGENT_PORT`, `AGENT_ALLOWED_IPS` (the portal's tailnet IP(s)),
`AGENT_MIGRATE_TIMEOUT_MS`.

The agent **refuses to start** if the token is missing, or if bound to `0.0.0.0`
with no IP allowlist.

## API

All endpoints except `/healthz` require `Authorization: Bearer <AGENT_TOKEN>` and
must come from an allowed IP.

| Method | Path | Purpose |
|---|---|---|
| GET | `/healthz` | Liveness (no auth) |
| GET | `/api/info` | Server name + supported operations |
| GET | `/api/sites` | List websites on this server (`wo site list`) |
| POST | `/api/op/:type` | Start an operation → `{ jobId }` |
| GET | `/api/jobs` | List recent jobs |
| GET | `/api/jobs/:id` | Job status |
| GET | `/api/jobs/:id/logs` | Full log buffer (JSON) |
| GET | `/api/jobs/:id/stream` | Live logs (SSE) |
| POST | `/api/jobs/:id/cancel` | Cancel queued/running job |

### Operations & params

- **deploy** — `{ domain, root, delete?, branch?, repo? }` (`root` required over
  the API — no interactive selector)
- **update** — `{ domain, branch? }`
- **delete** — `{ domain, confirm: true }` (the `confirm` flag replaces the typed
  `YES`)
- **alias** — `{ aliasDomain, mainDomain, branch?, repo? }`
- **cleanup** — `{ newDomain, oldDomain, mode? }` (`mode`: `audit`|`replace`|`verify`;
  `all` is rejected — it's interactive)

### Examples

```bash
TOKEN=... ; BASE=http://10.0.0.5:8787

# list sites on this server
curl -s $BASE/api/sites -H "Authorization: Bearer $TOKEN"
# => {"server":"AGENT_SEO_1","count":8,"sites":["a.com","b.com",...]}

# start a deploy
curl -s -X POST $BASE/api/op/deploy \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"domain":"newsite.com","root":"rootdomain.com"}'
# => {"jobId":"...","state":"queued"}

# stream its logs
curl -sN $BASE/api/jobs/<jobId>/stream -H "Authorization: Bearer $TOKEN"

# delete (requires confirm)
curl -s -X POST $BASE/api/op/delete \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"domain":"oldsite.com","confirm":true}'
```

SSE events: `hello` (on connect), `line` (`{t,stream,line}`), `state`
(`{state,reason}`). The stream closes when the job reaches a terminal state
(`succeeded`/`failed`/`timeout`/`cancelled`).

## Operation internals

Each operation in `src/operations/index.js` has `validate()` (strict — the
injection boundary) and delegates `run()` to its native module:

- `deploy.js` — resolve DB + CDN_PREFIX from the map, wo create, drop local DB,
  git clone, write `.env` (salts + constants), nginx + 15-job cron, perms, cache
  clear, SSL, SEO+CDN register; rotation (cleanup → delete → unregister) when
  `delete` is set and SSL succeeded.
- `alias.js` — inject `SITE_MOBILE_HOST` into the main `.env`, clone it, read
  `CDN_PREFIX`, swap alias values, nginx + 4-job cron, SSL, clear both caches,
  register.
- `update.js` — verify branch, hard reset, preserve `.env`, perms, Acorn warm,
  restart + reload, cache clear.
- `delete.js` — cron rm, kill domain procs (via `/proc`), locks, wo delete, rm
  site/nginx/certs, nginx test+reload, cron restart.
- `cleanup.js` — wp-cli search-replace with audit/replace/verify modes.

Values only ever reach array-arg `spawn` calls (never a shell) and a quote-safe
`.env` writer, so domains/passwords with shell metacharacters can't inject.

## Notes

- Jobs and logs are **in-memory** (retention `AGENT_JOB_RETENTION_MS`, default
  1h). The control panel is the durable record; a restart forgets history.
- `AGENT_MAX_CONCURRENT` defaults to **1** to serialize deploys (avoids
  nginx/php-fpm/DB races). Raise only if operations are known-independent.
- Secrets in job params (matching `pass|secret|token|key`) are redacted in job
  views and logs of params.
## Rotating the deploy secrets

The five deploy secrets (`ADVMO_DOS_KEY`, `ADVMO_DOS_SECRET`, `TELEGRAM_BOT_TOKEN`,
`SEO_MONITOR_TOKEN`, `CDN_API_KEY`) live in this portal's `.env` and reach a
server only at bootstrap. To rotate: change them here, restart the portal, then
Servers → **Push secrets (all)** (or per server: ⋯ → Push secrets). Each agent
writes them into its own `.env` and into every deployed site's `.env`, then
restarts itself. Values are never stored in the operation record.

## Rotating the agent key

`POST /api/op/rotatekey` `{ token }` replaces this agent's own bearer token
(`AGENT_TOKEN`). The portal generates the new key (Servers → ⋯ → **Rotate agent
key**, or **Rotate keys (all)**). The agent writes it to its `.env`, accepts it
at once **alongside** the old key, and restarts itself ~5 s later — after which
only the new key works. The overlap lets the portal read the job's result with
the old key and then switch. Like the other restarting operations it refuses
while another job is queued. The key is never logged.

## Agent log

`GET /api/agent/log?lines=500` returns this service's journal (`journalctl -u
streaming-agent`, up to 5000 lines): starts and stops, crashes, and one `[req]`
line per request that changes something or is refused — method, path, status,
caller IP; never a body or a header. Successful GETs are not logged. The portal
shows it under Servers → ⋯ → **View agent log**. Job output is not in the
journal; the portal keeps that per operation.

## Re-pulling DB credentials

`POST /api/op/dbcreds` `{ domain }` reads the `seo-domain-map` entry of the
site's recorded root domain (`SITE_ROOT_DOMAIN`) again and rewrites `DB_HOST`,
`DB_NAME`, `DB_USER`, `DB_PASSWORD` in the site's `.env` where they differ, then
clears the site's caches. Use it after the map changed (database moved, password
rotated). Nothing else in the `.env` is touched; the password is never logged.

The map's credentials are **tested from this server first** (a real `mysql`
connection to that database). If they do not connect, the job fails and the
`.env` is left exactly as it was — a stale map entry cannot take a working site
down. On success the previous `.env` is kept beside it as `.env.before-dbcreds`
(0600, outside the webroot).

## Security audit and hardening

`GET /api/security` is a read-only audit of this server (`src/lib/security.js`).
It reports facts and the findings drawn from them:

- **SSH**: effective settings (`sshd -T`), every key allowed to log in as root or
  a login account (type, size, fingerprint, comment — never the key body), the
  successful logins in the journal (when, account, password or key, address, key
  fingerprint) and failed attempts grouped by address, including refused keys.
- **Accounts**: every account that can log in, holds a key, has uid 0 or may
  sudo, with its keys from both `authorized_keys` and `authorized_keys2`. Flagged:
  a second uid-0 account, an empty password, a key or usable password on a
  service account, an account created or changed in the last 14 days, sudo
  members, and an `authorized_keys` file outside any account's home.
- **Firewall, fail2ban, listening ports** and which ports the internet can reach.
- **Updates**: pending security updates, automatic updates, restart pending.
- **Web user**: shell, password, own crontab, PHP files inside uploads folders,
  programs or scripts it owns in temp folders.
- **Database**: library files where MySQL can write, foreign functions loaded
  (`mysql.func`), accounts open to any address — the marks of a UDF attack.
- **Agent**: bind address, allowlist, `.env` mode.

`POST /api/security/keys/add { key }` installs a public key for root (a bare key
line only — no options); `POST /api/security/keys/remove { user, fingerprint }`
removes one. Removing root's last key is refused while password login is off.

`POST /api/op/harden { actions: [...] }` applies fixes, each idempotent:
`fail2ban`, `auto-updates`, `firewall`, `ssh-basics`, `env-perms`,
`ssh-keys-only`. **`ssh-keys-only` turns SSH password login off and refuses
unless root has a key installed and the SSH log shows a successful key login
for root** — proof the key works. Every sshd change is a drop-in that is
syntax-checked, read back and removed again if it did not take effect; ssh is
reloaded, not restarted, so open sessions stay open. `firewall` allows SSH
before it switches ufw on and names the public ports it will cut.

The agent itself now locks an address out for 15 minutes after 10 wrong keys,
logs why each caller was refused, logs every job's start and end, and keeps its
`.env` at mode 600. In the log view, `sudo`'s lines are hidden unless `?all=1`.

## Firewall

`GET /api/firewall` lists ufw's state and numbered rules. `POST /api/op/firewall`
changes it: `{ action: "allow", port, proto?, from?, tailnet? }`,
`{ action: "delete", number, raw }`, `{ action: "enable" }`, `{ action: "disable" }`.
Refused: removing the last rule that lets SSH in, removing the last rule that
lets the portal reach the agent, and opening the agent's own port to the
internet. `delete` needs the rule's text as well as its number, because numbers
shift when a rule is removed. `enable` allows SSH, web, Tailscale and the agent
(tailnet only) before it switches ufw on, and names the public ports it cuts.

## Always-allowed addresses (the panel's allowlist)

The proxies in front of the sites, plus anything the operator adds in the panel
(`src/lib/proxies.js`). Every visitor reaches nginx **through** the proxies, so
on each server these addresses are never banned (fail2ban `ignoreip`, in
`jail.d/wcp-allow.local`), always let through the firewall (one `ufw allow from`
rule each) and trusted by nginx for the visitor's real address
(`set_real_ip_from` in every site's `custom-cache.conf`).

The panel sends the list as `allowlist` with every `harden` operation; the agent
stores it in `allowlist.txt` beside itself (so deploys use it too) and falls
back to a built-in default until it has been sent one. The `trusted-proxies`
action applies it: rewrites the sites' includes (nginx is tested, and every file
is put back if it fails), names each address in ufw, removes the rules of
addresses taken off the list, and lifts any ban on them.

**The `fail2ban` action runs the SSH jail only.** Jails that watch web traffic
count the whole internet's bad requests against the proxy's address and ban it;
`recidive` then bans it on every port for a week, and every site on the server
answers 403 from the proxy. That happened on 17 Nov 2026 when this action simply
started fail2ban and WordOps' preconfigured nginx jails came up with it. The
action now reads the jail list from the configuration without starting anything,
switches every non-SSH jail off in `jail.d/wcp.local`, verifies only `sshd` is
running, and stops fail2ban again if anything else came up.
